**Product:** one practical personal Windows user's daily-operations app, existing Chairman and existing task/memory owners. Not enterprise IAM, multitenant, a second Chairman, or a duplicate task database.

## 1. Decision and narrow scope
Retain the independently reviewed R14-D2 architecture verdict: an independently authenticated, no-launch **source-data envelope** is defensible *conditionally*, and actual operational release remains **STATIC_REJECT / BLOCKED**. This D3 paper specifies ONE candidate out-of-band bootstrap and release grammar for future independent review. It is **not** owner endorsement, independent security clearance, implementation authorization or proof that a certificate, private key, verifier or trusted policy exists.

**Proposed choice:** an externally audited small **native Windows read-only verifier** using the OS-provided CNG primitives and an **out-of-band owner-approved ECDSA P-256 publisher public key**, with **per-release exact identity approval** instead of trusting candidate-declared offline dates/sequences. Implement no verifier branch until the specific initial verifier and publisher are really established and separately authorized.

## 3. Separately owned publisher signing key; custody, authorization and recovery

- One owner-approved signing identity **K1** (symbolic identifier only, NO KEY CREATED). Proposed algorithm: ECDSA over NIST P-256 with SHA-256. The approved public key is **65-byte uncompressed SEC1 form** (04 || X[32] || Y[32]); record fingerprint SHA-256 over ASCII bytes "VRES-OS/P256-PUBKEY/1" followed by a NUL byte and these 65 bytes. Independently authenticate and pin this exact fingerprint in a policy external to the candidate before any release verification. Validate point/curve and encoding. The candidate may repeat a key ID only as a checked equality claim, not as key selection.
- Private signing key is provisioned **only after separate explicit operator consent**, on a separately controlled offline signing device or independently protected non-exportable hardware token, distinct from W4 source checkout, regular user Windows execution path and repository/CI. Do not request any secrets in ChatGPT or write a private key to GitHub, candidate, manifest, user profile, logs or test roots. Custody, backup/loss response and signing approval evidence are separately reviewed before issuance. No enterprise IAM, certificate authority, HSM purchase, second Chairman or extra task store is assumed.
- Publishing role: a separately authenticated producer first completes a bounded source-only ZIP as **data**. The authorized publisher examines the exact ZIP bytes and independent release inventory, creates the external exact-byte manifest below and signs its hash with the provisioned offline K1. Sign nothing while provenance is unresolved. Key custody is separate from source editing and unsigned artifact creation even when one human ultimately owns both roles.
- Compromise/loss/rotation: **fail closed**; invalidate pending K1 release approvals, establish a new independently approved policy epoch and key K2 through the out-of-band channel, independently reapprove the first verifier/trust policy and exact next release. No candidate-controlled new-key list, cross-signed shortcut, mutable journal or in-repo emergency override. A stolen old offline approval record remains a replay risk if the trusted operator cannot establish the current policy epoch.

## 4. Cryptography and domain-separated exact signed bytes — proposed V1 contract

**Library:** Windows CNG through Microsoft-supplied bcrypt.dll and documented BCryptImportKeyPair / BCryptVerifySignature, using ECDSA P-256 and SHA-256. No candidate-supplied DLL, Python crypto module, package download, alternative provider or manifest-selected algorithm. Independent cryptographic interop/security testing still required; this paragraph is not a witnessed CNG positive result.

**Three separate DATA files**, with no self-reference: complete finalized source ZIP; external ASCII manifest; exactly 64-byte detached ECDSA signature. The manifest/signature MUST NOT be members of the ZIP whose whole-file digest the manifest binds. The ZIP itself may legitimately contain the original owner's SOURCE-MANIFEST.json as ordinary covered member data.

**Signature input** is precisely ASCII "VRES-OS/W4/SOURCE-ONLY/SIG/1", a 0x00 byte, an unsigned 64-bit **big-endian** integer giving the exact manifest byte length, and the **unmodified manifest bytes** in this order. Compute SHA-256 of this entire byte string. Sign that 32-byte digest with ECDSA P-256. The detached signature is exactly 64 raw bytes: 32-byte big-endian r followed by 32-byte big-endian s, **not ASN.1 DER**. Reject any length, curve, key, format or algorithm mismatch; require valid CNG public-key import and signature check. The review must explicitly test cross-tool CNG interoperability; no test signature is an approved publisher signature. SHA-256 bytes/digests and RSA/Git SHA-1 identifiers by themselves are not publisher authentication.

**Proposed external manifest grammar, not yet independently accepted:**
- ASCII **only** bytes (valid UTF-8 subset), **no BOM**, CR, tabs except the two required tab separators in entry rows, NUL, comments, blank lines, trailing bytes or ambiguous whitespace. Exactly one LF (0x0A) terminates every line including last "END". Maximum manifest size **256 KiB**.
- First line is exactly "VRES-OS/W4/SOURCE-ONLY/MANIFEST/1". Then unique fixed-order fields, each ASCII "name=value" plus LF: repository, product, purpose, channel, key-id, policy-epoch, release-sequence, source-commit, source-tree, accepted-base, zip-byte-length, zip-sha256, source-manifest-sha256, dependency-closure, launch-authorized, owner-count, migration-count, member-count. No optional or unknown fields, no duplicate labels, no JSON canonicalization, no duplicate name case variants. Fixed values are repository=vosser24/Vres-OS, product=Vres-OS, purpose=SOURCE-ONLY, channel=PERSONAL-W4, dependency-closure=UNRESOLVED, launch-authorized=NO. owner-count=13; migration-count=41; member-count <=354. Numeric fields are canonical nonnegative base-ten digits, "0" or a nonzero leading digit and remaining digits, bounded for each field. SHA-256 is lowercase 64-hex; Git IDs are lowercase 40-hex metadata **only**.
- Then exactly owner-count rows: "owner=" + canonical relative path + TAB + lowercase 40-hex Git blob OID + LF; sorted strictly by unsigned ASCII path bytes, unique. These 13 owner identities are compared to an independently authenticated allowlist and separately established full SHA-256 of actual covered owner-source bytes, never trusted because the manifest asserts them.
- Then exactly 41 migration rows: "migration=" + approved relative source path + TAB + lowercase 64-hex SHA-256 + LF; 001–041 only, sorted by path, compared to an independently approved original-owner inert digest set. No 042+ or migration execution.
- Then exactly member-count rows: "member=" + canonical ZIP relative member name + TAB + canonical byte length + TAB + lowercase SHA-256 of uncompressed exact member bytes + LF; sorted by unsigned ASCII member path bytes, unique. The internal SOURCE-MANIFEST.json SHA-256 field must equal its listed member hash and its actual bytes.
- Final line exactly "END". Relative paths use ASCII letters, digits, dot, underscore, hyphen and forward slash only. Reject empty/dot/dot-dot segments, leading slash, doubled slashes, trailing dots/spaces, devices/reserved DOS names, colon/ADS, backslash, UNC, case-insensitive collisions, symlinks, links/reparse members or unexpected mode/type. Final exact grammar and actual source path compatibility must be independently reviewed before coding.

**ZIP bounds:** ZIP byte length at most **64 MiB**, each source member at most **15 MiB**, no more than 354 members and no inflated total beyond 64 MiB; no ZIP64, encryption, compression, comments, extra fields, duplicate names, path aliases or symlinks. For R13 reproducible provenance, begin with **ZIP_STORED** and the original owner-specified deterministic metadata; independently confirm those exact accepted bytes before freezing any compatibility rule. Reject local-header/central-directory conflicts, overlapping segments and trailing data. Verify SHA-256 of the **actual opened ZIP bytes**, each actual member and all signed metadata. These are initial budgets, subject to independent full original-owner inventory compatibility review, not claims about an actual ZIP.

## 5. Offline exact-identity policy: choose no clock-dependent auto acceptance

**V1 recommendation is exact, one-shot out-of-band owner approval per candidate, NOT a generic signature-only or candidate sequence policy.** The owner-approved protected record must bind: policy epoch, externally approved K1 fingerprint, trusted verifier executable SHA-256, exact manifest SHA-256, exact complete ZIP SHA-256, selected source commit/tree, permitted no-launch purpose and release sequence. Trust policy is distributed/authenticated **separately from the candidate**. The candidate cannot update policy or select keys, time sources or algorithm.

The release sequence and any signed_at/not_after appearing in candidate data would be **informational, never authorization** unless a later independently reviewed trusted-time policy exists. In this first grammar, omit timestamp fields entirely. In offline mode with no authenticated current epoch or exact OOB approval, return TRUST_POLICY_NOT_ESTABLISHED / REFUSED; never accept old release solely because its signature remains mathematically valid. Retain old approvals for audit, not automatic allowlisting; exact obsolete approvals require an independent human/policy-epoch rejection. Do not claim automatic anti-replay or revocation propagation without protected monotonic state. A future independent protected sequence/revocation state and clock is **separate, held**.

## 6. Authenticated producer vs read-only consumer: break circularity

**Producer (NOT_BUILT):** first establish the independent origin of source-only producer/owner inputs on a separate protected build/signing boundary. An authenticated source-only packager must bind the exact approved W3 R2 base, R13 HEAD/TREE and 13 original-owner blobs, plus an independently verified SHA-256 file inventory. It may not execute any untrusted candidate W4 Python, patch the R13 staging hold, use original release_artifact.stage(), write to the user's installed tree, run Git hooks, call PostgreSQL or create a pretend ZIP. It creates the full source-only ZIP **before** signing external manifest. The exact publisher/build procedure and actual original-owner ZIP reproducibility remain PENDING and require their own clearance.

**Phase A consumer (NOT_BUILT):** the separately authenticated verifier opens only one explicitly selected, permitted, non-sensitive ZIP + external manifest + signature and its independent policy; no HOME/profile scan. Hold filesystem handle identity, reject reparse/symlink/hardlink/ADS and unsafe NT names, read within bounded memory, authenticate signer/policy and exact consumed bytes, inspect ZIP as inert data. The only possible positive outcome is AUTHENTICATED_SOURCE_CANDIDATE_DATA_ONLY (no launch, install, extraction, temp output, staging, mutation, Python import, subprocess, native Claude, hook or database). After closing a handle, a former pathname is not authenticated for future use.

**Phase B (HELD):** only after real Phase A trust is established, separate independent security acceptance and **NEW** operator consent, a trusted orchestrator may validate real original-owner source in memory and independently reproduce ZIP SHA-256. Preserve original release_artifact.verified_source/source_manifest_bytes, release_inputs.release_record_problems and W3 owner identities. No R13 refusal monkeypatch, no original stage() or POSIX BoundOutput publication. Must reauthenticate the exact bytes at consumption.

**Phase C (HELD):** distinct Windows NT handle-relative publisher with ACL/ownership/volume/reparse/junction/hardlink/rename/ADS/case/UNC/post-close/crash evidence and its own consent. Never infer safety from POSIX methods, a past hash or directory path. No destructive interrupted-stage rollback.
