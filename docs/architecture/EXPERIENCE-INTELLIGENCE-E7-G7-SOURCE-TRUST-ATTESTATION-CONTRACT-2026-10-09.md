## 1. The gap (confirmed by source reading)
1. `source_register` (MCP, `mcp_server.py`) forwards a caller-supplied `authority_level` to `SourceService.register_in_conn`, which inserts it unchanged into `vres.sources.authority_level` (`text`, no CHECK, no allowlist; `001_initial.sql`). Project-local registration (`project_id` not NULL) requires no approval; only company scope calls `require_company_approval`.
2. `SourceService.add_chunks` lets the same caller attach source text. `content_hash` on the source is caller text and is never recomputed.
3. E5 retrieval policies v2–v5 (`experience_retrieval.py`, `RAW_SOURCE_AUTHORITY_ALLOWLIST_V2 = ("trusted_project_source",)`) admit a source-owned raw chunk when `s.authority_level = ANY(allowlist)`. The comment in source states the label is free text; the allow-list is fail-closed over *values* but the value is caller-set. A caller can therefore register content with `authority_level='trusted_project_source'` and obtain E5 raw-source eligibility with no verification.
4. Registration dedup keys on caller `content_hash` + project + `source_type` + `authority_level` + `version` (`sources.py`). Identical text under different labels yields separate sources; a matching caller hash returns an existing source key without checking the new content.
5. E1-v2 observed capture requires `authority_level == 'external_untrusted_observation'`; that label is only ever restrictive (downgrade direction).
6. E1-v1 participated capture and E2 do not read `sources.authority_level` at all (trust derives from task validation); source trust reaches them only through G1 (separate).

Verdict: **G7_CALLER_TRUST_GAP CONFIRMED. E5_RAW_SOURCE_IMPACT CONFIRMED** (raw-source *visibility* is gated by a caller-asserted label; ranking, role and knowledge authority are not affected).

## 2. Concepts kept separate
| Concept | Owner today | G7 stance |
|---|---|---|
| Declared source information (type, title, origin, label, caller content_hash) | caller | descriptive only; never positive trust |
| Verified source identity/content | none | **new**: owner-derived digests (§5) |
| Authorized trust assignment | none | **new**: immutable ledger row, issued by a protected function only when an immutable user-authored event contains the exact subject text (§4) |
| Effective trust used by readers | label comparison in E5 | **new**: one read-time function (§6) |
| Visibility vs knowledge authority vs participation vs content truth | E5 / E3 / E1 / nobody | unchanged. Trust assignment never proves content is true; attested ≠ authenticated |

Registration is not verification. A user approval records an explicit human trust decision about an exact source version; it is not cryptographic proof of authenticity. A *technically verified origin* kind (signed/provider-verified acquisition) has **no existing verifiable mechanism**; the ledger reserves `basis='provider_verified'` as NOT_AVAILABLE and refuses it until a real mechanism is designed. Nothing is manufactured from model prose.

## 3. Threat model
T1 caller labels poisoned text `trusted_project_source`. T2 caller registers then later appends/edits chunks after a legitimate attestation. T3 caller reuses a hash/label to dedup onto an attested source. T4 a general or other-subject approval is replayed as a trust grant. T5 company-scope approval used for a project grant (or reverse). T6 cross-project/cross-user source or approval. T7 forged approval row or forged ledger row by a restricted DB role. T8 race between registration, attestation and chunk writes. T9 stale trust after revoke/supersession/scope change. T10 legacy rows silently inheriting trust. T11 forged host-hook ingress: an agent or process with shell access as the same OS user runs the UserPromptSubmit hook CLI with a fabricated prompt, which the writer credential then stages as a genuine `source='user_prompt'` event (source-read in `plugins/vres-os/hooks`, `hooks.py`, `session_prompts.py`; not executed). Out of scope: superuser/owner-role compromise (trusted computing base), content truthfulness, G2 common lineage.

## 4. Preferred mechanism
**Reuse**: the exact-subject convention (type + subject key, as in `require_approval` and `source_revocation`), but not the runtime-writable `approval_events` rows as authority; host-protected user instruction events (`task_events` USER_INSTRUCTION writable only by the provenance writer role, mig. 023/024), and the protected-function methodology of migration 040 (SECURITY DEFINER, `SET search_path`, `REVOKE ALL … FROM PUBLIC`, privilege sweep, append-only). **New**: one append-only ledger plus two functions.

Ledger `vres.source_trust_events` (append-only; UPDATE/DELETE/TRUNCATE rejected by trigger for every role):
`id`, `event_key`, `project_id NOT NULL`, `source_id`, `source_key`, `action ∈ {grant, revoke}`, `basis ∈ {user_approval}` (`provider_verified` reserved, refused), `policy_version='176.g7.v1'`, `policy_digest`, `content_digest`, `descriptor_digest`, `subject_key`, `user_event_id`, UNIQUE(`user_event_id`,`subject_key`), `supersedes_event_id`, `expires_at NULL`, `idempotency_key UNIQUE`, `created_at`. Constraints: grant requires both digests; project scope only.

Ledger write guard (precise): runtime and PUBLIC hold no INSERT/UPDATE/DELETE/TRUNCATE on the ledger (explicit revoke after default privileges, §8). Defense in depth: a `SECURITY INVOKER` BEFORE INSERT trigger on the ledger raises unless `current_user` equals the migration/owner role; the trigger function must be INVOKER, because inside a definer function `current_user` is the owner (the legitimate case), while a direct runtime-role INSERT has `current_user` = runtime role. Immutability triggers for UPDATE/DELETE/TRUNCATE reject every role. No trigger or rule is added to `approval_events`, which G7 neither reads nor writes.

Functions (owner = migration role; runtime role gets EXECUTE only, no ledger DML):
- `vres.record_source_trust_decision(p_task_key, p_project_id, p_source_key, p_action, p_user_event_id, p_expected_content_digest, p_expected_descriptor_digest)` is the **single** write path (issuance and revocation). It locks the source row `FOR UPDATE`, requires `status='active'` and `project_id = p_project_id` (company scope refused), **recomputes both digests inside the database**, refuses on mismatch with the expected values or when no chunk is persisted, and recomputes the exact subject key `source_trust:<action>:<project>:<source_key>:<content_digest>:<descriptor_digest>`. Its only authority anchor is `p_user_event_id`, and the anchor must prove *what the user said*, not merely that a user spoke: that `task_events` row must be `event_type='USER_INSTRUCTION'`, `actor='user'`, belong to the named task and project, be the **latest** USER_INSTRUCTION of that task, have `payload.source='user_prompt'` (a prompt the user typed; events with `source='ask_user_question'` are refused because the option text is authored by the runtime and the user only clicks), **and its stored user text (`payload.text`, written only by the provenance writer role and immutable, migrations 023/024) must contain the recomputed subject key verbatim together with the action word**. The function never consumes or writes `approval_events`. Because the subject key embeds digests the database has just computed, a runtime-role session that obtains the genuine latest event id (it can SELECT `task_events`) still cannot satisfy the function unless the *user* typed that exact subject in a real instruction; the *database* runtime role cannot author, alter or reorder user events (it cannot satisfy the writer-role gates of migrations 023/024). The ingress by which the user-event store itself is fed is a separate dependency, declared in T11/R5. "Latest" follows the `approvals.py` convention and is stricter: the anchor must be the newest `actor='user'` USER_INSTRUCTION of the task by `(created_at DESC, id DESC)` over **all** sources, and no USER_CONTROL event of the task may be newer than it. Any later user event of any kind (a typed message, an AskUserQuestion answer, a control command, a refusal) makes the anchor stale and the function refuses; the Chairman must therefore not ask a question between the user's subject message and the call, and a stale anchor means the user states the subject again. This can only deny, never elevate. `UNIQUE(user_event_id, subject_key)` bounds replay (one event may carry several subjects, one row each). Idempotent on `idempotency_key`. Residual R4: typed prompts reach the event store after the host's redaction transform; subject keys use server-generated `SRC-<hex>` source keys and hex digests, which the transform leaves unchanged (observed for a representative subject), so the match is stable. Residual: if the user pastes a subject without intending it, or a hostile tool result induces the user to do so, the database cannot tell (R1); the Chairman must show the exact subject text and never pre-fill it into a user turn.
- `vres.source_effective_trust(p_source_id)`: read function (§6).

Existing-path facts (verified) that shaped the design: (a) `approval_events` has no write-protection trigger (none in migrations 006–046); (b) `database_boundary.py` grants the runtime role `SELECT,INSERT,UPDATE,DELETE` on all current and (via `ALTER DEFAULT PRIVILEGES`) future vres tables, SELECT on `task_events`, and EXECUTE on functions; (c) acceptance wording is validated only in Python (`explicit_acceptance`). Design response: `approval_events` is not an authority input and is not touched (so no guard is needed and none can be vacuous); the single issuing function is reachable by the runtime role by design, so its authority must come from something the runtime role cannot author: the immutable user event text containing the exact, database-recomputed subject. Residual R1: the database proves the user wrote this exact subject in the latest instruction, not that they understood or intended it.

The conversational flow is: Chairman states the exact source, project, digest and action; the user answers; the user replies with a message that includes the exact subject text (copied from the Chairman's proposal); Python may pre-check the wording for a clear refusal message, but the authoritative check is the database's text match on the latest user event; the single function is called with that event id. A general `source_publish`/`revoke_source`/company approval is a different `approval_type` and a different subject and the function never reads it (test E).

**Rejected alternatives**: allow-listing label values (still caller text); a `sources.trust` column written by the service (a DB writer with UPDATE bypasses it); re-using `scope_approval_event_id` (it proves company publication, not trust); a signed Python token (no key custody in the architecture); making `source_register` mint trust when given an `approval_key` (couples registration to trust); automatic trust for onboarding-registered sources; trust inferred from `content_hash` equality.

## 5. Content and descriptor binding
- `content_digest` = SHA-256 over `project_id`, `source_key`, and the list of `(ordinal, sha256(content))` of all persisted `knowledge_chunks` of the source, sorted by `(ordinal, sha256(content))` ascending (a deterministic total order, because ordinals restart per `add_chunks` call), **computed in the database from the stored `content` text**, not from the stored `content_hash` column and never from caller `sources.content_hash`.
- `descriptor_digest` = SHA-256 over `source_type`, `origin`, `version`, `project_id`. Title and `path_or_uri` locations are descriptive and unbound (a moved file does not change identity; recorded in §14 as a deliberate choice). Caller `content_hash` and `metadata` are not bound or trusted.
- A source with zero chunks cannot be attested (nothing to bind); fail closed.
- Chunks added, edited or removed after attestation change the digest, so trust becomes *stale* at read time with no write needed. Source revoked, inactive, or moved scope (`project_id` change) also removes trust.
- Same content under different labels: attestation is per `source_key`, so no label or hash can borrow it. Recommended hardening: registration dedup must skip any source with a grant, so a hash match cannot route new chunk writes onto an attested source (the digest would go stale anyway; this removes the surprise).
- Concurrency: `FOR UPDATE` on the source row conflicts with the `FOR SHARE` taken by `require_active_source` in every chunk and evidence writer (the registration-time `source_locations` insert does not take the lock, but locations are unbound by `descriptor_digest`, so the digest is unaffected), so a chunk write either commits before the digest is computed (included) or after the grant (digest becomes stale). An advisory lock `source-trust:<source_id>` serializes concurrent issuance.

## 6. Effective trust (single reader contract)
`vres.source_effective_trust(source_id)` returns one of:
`verified_trusted` — latest ledger event for the source is an unexpired `grant` (not superseded/revoked), policy identity current, source `status='active'`, project matches, **and** freshly recomputed digests equal the granted digests, and the declared label is not `external_untrusted_observation`;
`unverified` — everything else (no event, stale, revoked, corrupt, unknown policy, company scope, zero chunks, conflicting evidence). Anything not provably `verified_trusted` is `unverified` (fail closed). The caller label can only *further restrict*: declared `external_untrusted_observation` plus a grant is a conflict and resolves to `unverified`.
Readers never compare `authority_level` for positive trust again.

### Trust-state machine
`UNATTESTED →(grant + approval)→ ATTESTED_CURRENT`; `ATTESTED_CURRENT →(chunk/descriptor change)→ STALE (derived, no write)`; `→(revoke event)→ REVOKED`; `→(source status revoked via source_revocation)→ SOURCE_REVOKED`; `→(new grant, new digests)→ SUPERSEDED/ATTESTED_CURRENT`. STALE returns to CURRENT only through a *new* grant for the new digests; an old approval never transfers.

## 7. Entry points
Issuance: only `record_source_trust_decision` (called by new MCP tools `source_trust_grant`, `source_trust_revoke`). No other path writes the ledger. `source_register`, `add_chunks`, onboarding and `company_source_register` write no trust.
Consumption (inventory): E5 raw-source fallback (`experience_retrieval.py`, allow-list at the `s.authority_level = ANY(%(raw_auth)s)` join; policies v2–v5); `knowledge.py` source display (`s.authority_level`, display only); E1-v2 observe (label equality, restrictive, unchanged); `experience_benchmark*` harness code that writes labels (test harness, not product authority); onboarding writes `'unknown'`. E1-v1/E2 do not consume source authority (G1 territory). `source_revocation.py` remains the only writer of `revoked` and is unchanged.

## 8. Database and privilege design
Verified from `database_boundary.py` (read at `0b4d5cd`): the runtime role holds `SELECT,INSERT,UPDATE,DELETE` on all vres tables, `USAGE,SELECT,UPDATE` on sequences and EXECUTE on functions, now and by default privileges for objects created by the migration role. Therefore new objects must **explicitly revoke**: the ledger, its sequence, and the new functions get `REVOKE ALL … FROM PUBLIC` and the migration-040 privilege sweep (revoking the default-privilege grants from the runtime role on the ledger table/sequence and on the internal helper functions); only `record_source_trust_decision` and `source_effective_trust` receive EXECUTE for the runtime role, and that grant must also be added to `activate_boundary` so it survives boundary repair. Ledger immutability is enforced by triggers for UPDATE/DELETE/TRUNCATE for every role, and the INSERT guard of §4 is a SECURITY INVOKER trigger (never definer). Existing trigger functions in migrations 023/024 use `session_user` because their legitimate writer is a distinct login; here the legitimate writer is a definer function, so the INVOKER/`current_user` rule applies and is tested directly (matrix O). Objects are owned by the migration role; functions are SECURITY DEFINER with `search_path = pg_catalog, vres`. Provenance-writer, runtime and migration roles remain distinct. Chunk 1 starts with a grants-inventory test asserting the runtime role has no INSERT/UPDATE/DELETE/TRUNCATE on the ledger and its sequence, that a direct INSERT is rejected by both privilege and trigger, and that the issuing function succeeds only through the text-anchored path; a failure there is stop-and-redesign. The test needs a real restricted runtime-role LOGIN. `tests/integration/conftest.py` already has a `provenance_writer` fixture (`trusted_provenance_writer.py`, a least-privilege writer role) and `test_e40_attestation_split_role_journey.py` exercises `provision_boundary`/`activate_boundary` with a runtime login; Chunk 1 reuses those patterns, and a dedicated runtime-login fixture for the ledger tests is part of Chunk 1 if the existing journey fixture is not directly reusable.

## 9. Legacy data and rollout
Every existing row is `UNATTESTED`; **no automatic grandfathering**, including onboarding rows (`unknown`) and any `trusted_project_source` label. A read-only audit tool lists sources the v5 policy would admit by label with chunk counts and digests; the user may grant per source (one approval per exact source/digest). Approval is per exact source/digest only: one user message may contain several subject lines and each yields its own ledger row; there is no set-digest subject.
Rollout without a misleading claim:
- Stage 0: ledger + functions + audit tool; **no reader behavior change**. Documentation states that v5 raw-source eligibility remains caller-label based ("unverified legacy mode").
- Stage 1: E5 policy v6 exists and is selectable; v2–v5 stay byte-identical (frozen replay).
- Stage 2: v6 becomes the default only after the user has reviewed the audit list. Until then no document may say E5 raw-source is verified-trust gated.
Effect on legitimate memory: knowledge-owned chunks, episodes, lessons and E1-v2 observation are unchanged. Project-source raw text needs one explicit grant per source; company-scope sources get **no** raw-source eligibility in v6 (company attestation is deferred behind the held company-publication flow). That is a real usability cost, recorded as Q2.
Old rows, `experience_policy_versions` digests (`176.e1.v1`, `176.e1.v2`, `176.e2.v1`) and E5 v2–v5 digests are untouched.

## 14. Residual risks, unverified items, open questions
- R1: the database proves that the latest typed user prompt contained this exact subject text; it does not prove the user understood or intended it (pasted text, hostile content the user copies). Python's wording pre-check is advisory only and is not an authority input.
- R5 (declared dependency, not closed by G7): all user authority in Vres, including this anchor, is only as strong as the integrity of the hook ingress that feeds the user-event store. A Chairman with shell access can in principle invoke that ingress with attacker text (`docs/KNOWN-LIMITATIONS.md` excludes an operator with arbitrary shell access). G7 closes caller-text, label, DB-role and approval-row forgery; it does **not** close hook-ingress forgery. Consequently no document may claim G7 makes trust unforgeable by the agent; it makes it unforgeable *by data and by the database runtime role*. Hook-invoker authentication is a separate hardening item (G8, not designed here) and is a prerequisite for any claim of full security acceptance beyond limited source-scoped containment.
- R3 (unverified): the exact payload key holding user text (`payload.text`) and its immutability were read in migrations 023/024 but not executed; if the text is not stored in the immutable event, the anchor design is unsound and Chunk 1 must stop and redesign. Usability cost: the user must include a long exact subject (two 64-hex digests); see Q6.
- R2: owner-role or superuser compromise is out of scope.
- Unread/unverified (role grants are now read, §8): `onboarding.py` re-scan interaction with digests; whether other readers (`knowledge_search`, semantic search) rank by `authority_level` beyond display (display use at `knowledge.py:255` only was found); E3 policy rows beyond E5; read-time digest cost on large sources (E1 chunk budget is 200; E5 hit sets are bounded but not measured).
- Q1: is `descriptor_digest` binding of `origin`/`version` too strict for re-registration flows?
- Q2: accept that company-scope sources have no raw-source eligibility in v6 until a company attestation design exists?
- Q3: should `expires_at` be used by default, or only content staleness and revocation?
- Q4 (resolved in this revision): per-source subjects only; no set-digest batch.
- Q6: is requiring the full subject text in the user message acceptable, or a shorter subject token?
- Q5: provider-verified origin: no mechanism exists; keep reserved and refused?
