## 1. N-1 — Who authenticates role-registry changes? Root-only authority, recovery-quorum and reserved signers

### 1.1 Authenticated genesis and independent root-of-roots

Accepted V1 §3.1 enlists E/V/CAS/W. That is NECESSARY but a compromised CAS/head signer must not be able to add a new E/W/V or authorize replacement of its own key. The independent H_0 ceremony therefore MUST bind a **separate immutable root-of-roots verification record**, whose protection is not derived from the CAS issuer or current same-user account.

H_0 proposed typed fields (DESIGN ONLY, NO KEY CREATED): canonical \`machine_id\`, Windows SID and protected installation instance identity; \`root_identity\`, \`root_fingerprint\`/key identifier, algorithm/evidence schema/version, public verification root and externally attested provenance chain, \`root_epoch\`, valid issuer domains and specific authority \`ROLE_REGISTRY_UPDATE\`, \`ROLE_REGISTRY_REVOKE\`, \`ROLE_REGISTRY_ROTATE\`, \`ROOT_RECOVERY\`; policy for authentic initial enrollment/display binding, monotonic epoch and rollback resistance. The actual root fingerprint MUST be shown/protected at provider-owned enrollment through independently authenticated out-of-band root trust, checked against the same source publisher/loaded governing baseline, and committed to independently protected H_0. Agent-selected fingerprint/local Git/CurrentUser certificate/thumbprint, DPAPI-only state and self-signed first-use assertions are NOT acceptable bootstrap. If no independently trusted anchor or displayed enrollment proof exists: **BLOCKED_BOOTSTRAP_ROOT_UNAVAILABLE**; no H_0, no positive issued record.

**Root key must be distinct from CAS/nonce service key.** A CAS key may sign only \`HEAD_ANCHOR_TRANSITION\` under registered authority and NEVER an UPDATE_ROLE_REGISTRY or ROTATE_ROOT claim. A current E/V/W signer may not add, revoke or silently replace any issuer key; all records are validated using the last independently authenticated root and registry epoch, not from a candidate's proposed file or a future signer field supplied by a model.

### 1.2 Registry update, recovery and revocation order

New rooted \`ROLE_REGISTRY_MUTATION\` event: full prior H_n/head SHA+epoch, root epoch and role-registry SHA, explicit ADD/REVOKE/ROTATE role set with old/new key fingerprints and purpose scopes, signer identities, revocation generation, target SID/install, operator event purpose, independently shown human consequence fields, independent root nonce and bounded provider time. **Only the independently authenticated root principal OR a separately rooted threshold/quorum of specifically enrolled protected recovery principals** may authorize a registry mutation. Recovery quorum members and quorum policy need their OWN verification roots, principal key IDs, purpose/epoch/target/capability and compromise path pinned at original H_0/current separately rooted head; a compromised CAS, E, V, W or withdrawal key alone cannot satisfy a quorum. No exact quorum number, key algorithms or vendor chosen until real independent service evaluation.

A protected change must be **atomic within H_n role/nonce/revocation ordering**: authenticate independent root/quorum and complete display, check prior registry and root epochs, consume mutation nonce and version/role changes, publish revoked keys and their pending E/V/W/Q invalidation together; blocked on concurrent CAS/Q, stale E/W/V, divergent registry or untrusted clock. If root/quorum origin, independence, atomicity or surviving trustworthy recovery is absent, **BLOCKED_ROLE_REGISTRY_MUTATION_UNVERIFIABLE** — never self-rotate, delete a compromised role silently or auto-clear Q. Historical events keep exact issuer version+revocation disposition and cannot be used as new LIVE authority.

**Root compromise/loss:** if the root and independently enrolled recovery quorum cannot be authenticated by means outside T2, the provider CANNOT invent a new genesis/current-user install instance or fall back to CAS issuer. The current F1 SWITCH MUST STOP; real out-of-band independent re-enrollment/lineage rollover is a separate future reviewed ceremony, not an operator chat reply.
