D2 — Durable project/source trust, explicit revocation. Valid approval is bound to exact project/source/content/descriptor and accepted provenance, not the lifetime of the recording task. Completion, cancellation, unbinding or reopening does not itself revoke an otherwise valid approval. Explicit revoke or invalidating drift removes that approval as a basis for trusted retrieval. Keep immutable grant/revoke evidence; recompute dependent knowledge eligibility and affected caches/embeddings, preserving independently supported eligible knowledge. Distinguish E7 trust revocation from E4 source lifecycle retirement/revocation; neither is a blanket purge. Ambiguous provenance is unverified. Preserve the existing authoritative trust ledger and governed learning (#176). Conditional cross-task revoke in the same project requires fresh explicit user authority; original host integration remains unverified. A narrowly scoped operator route in the same application is fallback only if needed. No model-originated issuance, stale event or unauthorized direct ledger/sequence modification. Retain necessary effective-trust/evidence reads, reconcile inherited/default privileges and table/sequence/routine grants without blanket regrant. Positive issuance authority remains held.

D3 — Preserve cancellation and reopening. Cancellation requires fresh explicit user authority for the actual task/session/current observation; atomic lawful terminal transition, immutable authority/status/session history, detachment and affected validation/work state. Reject replay, wrong scope, stale or model-only authorization and direct unauthorized terminal mutation. Reopening is a separately authorized legal transition, not deletion of prior evidence or automatic rebinding of stale authority. Preserve existing offline personal lifecycle and eventual original DB-backed task functionality; they are distinct contracts. R37 terminal holds remain; no dormant writer activation or removal of cancellation/reopening.

D4 — Explicit operator-only migration/provisioning. Ordinary application, project startup/adoption, CLI, MCP, hooks, tasks, repository, self-test and diagnostics must not implicitly migrate, provision or initiate secure operator setup. Incompatible runtime must refuse safely and identify the separate operator requirement. Preserve existing secure setup interface as explicitly invoked and purpose-bound; runtime privileges independently deny schema mutation. Reconcile all direct and indirect routes, child processes and administrative side effects at future authorized implementation/acceptance; targeted static review is not proof of complete dynamic call closure. No interlock removal.

Require explicit purpose, approved target/cohort, purpose-specific nonfallback credentials, independent enrollment and actual instance/database/effective-role verification on the connection doing the work, with consistency/coordination and revalidation on change. Endpoint, name, OID, system identifier, ledger fingerprint, shell flag or external preflight alone cannot distinguish all wrong/cloned targets. Test/staging/recovery must not inherit normal configuration, routing variables or live Credential Broker defaults; missing target refuses. For separately invoked backup/restore clients, constrain and verify their actual connections equivalently; a separate Python preflight does not prove client identity. No secrets in evidence. If identity/isolation cannot be established, stop. No database contact authorized.

D6 — Preserve original same-install update and separate preparation, switching, activation. The held old native host cannot be the dependency for repairing itself. Prepare verified artifacts without activating old hooks; establish executable/policy/effective registration and comprehensive relevant route isolation before any separately authorized native invocation. A stopped single service does not establish isolation. Keep existing install/update transaction, installed P2, rollback artifacts and manifest integrity; no hot patch or manifest rewrite. Obtain separate consent before installed/profile mutations. Application pointer rollback is not schema rollback; only activate a verified safe runtime/schema pairing. No alternate installer, build/staging execution, service action or native launch now.

Owner-directed source/design review does not supersede independent assessment and trusted positive authority for the two incidents. Use existing evidence first. Attributable authenticated reviewer or independently verifiable attributable report; AI advice or owner-account relay is not independent authority. THREAT_MODEL, RELEASE_DESIGN and operation-specific OPERATIONS remain separate; record findings, contrary evidence, scope and limits. For any insufficient evidence, identify smallest concrete missing item, favor noncontact sources; no routine repeat R38 or generic AI review. Before a held operation, independently establish applicable evidence and operation-specific clearance, then obtain explicit owner authorization for exact target, purpose, prerequisites, isolation, stop conditions and evidence retention. No blanket investigative exception. If prerequisites cannot be established, remain held. Each incident requires its own disposition; one permission does not authorize another.
