## 10. Refined source-only analysis: cross-task E7 revoke is possible in SQL, but the original host path remains UNVERIFIED

**Important correction/limitation to §9, based on a further exact immutable-source read:** A grant bound to a task later cancelled is **not necessarily irrevocable**. Historical E7 `record_source_trust_decision(...)` checks the *authorization event's* `task_id` against the **task selected by the new request's `p_task_key`**, and verifies that this task belongs to the source project. In its **revoke** branch, it finds the active prior grant using source identity plus stored content/descriptor digests and absence of a superseding revoke — **without requiring the prior grant's `task_id` to equal the new revocation task ID**. It then appends a revoke row whose `supersedes_event_id` points to the previously active grant. Source: [immutable E7 migration 047, lines 133–186 and 215–234](https://github.com/vosser24/Vres-OS/blob/d930adfa89617067115d9538e9692945230d9630/src/vres_os/migrations/047_source_trust_ledger.sql#L133-L234). The E7 048 trust reader requires the newest trust-ledger action to be `grant` and no such revoke, so an independently valid, newly appended revoke would change the read result to `unverified` without altering immutable grant history. Source: [immutable E7 migration 048, lines 27–64](https://github.com/vosser24/Vres-OS/blob/d930adfa89617067115d9538e9692945230d9630/src/vres_os/migrations/048_source_effective_trust.sql#L27-L64).

**Original R13 interaction:** Its strict `commit_user_inputs` source checks that the selected session is bound to a task with `status IN ('active','waiting_user','blocked')` and that the staged observation belongs to the session/task. Source: [immutable R13 migration 046, lines 60–110](https://github.com/vosser24/Vres-OS/blob/ad4c517aa1c14be9d64ddbfce4ad1eeb492cb46c/src/vres_os/migrations/046_original_observation_rebind_quarantine_r13b.sql#L60-L110). Original R13 047 cancellation detaches sessions from the **cancelled** task, so creating a *new* valid direct user `USER_INSTRUCTION` on the cancelled task via the ordinary strict writer is not established as available. However a **different, properly bound unfinished task in the same project** could theoretically produce the new exact authority event required by historical E7's cross-task revoke writer. This is a **conditional SQL source-path observation**, not proof of a working user-facing revoke operation.
