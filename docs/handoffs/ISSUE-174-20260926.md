## Frozen product decisions

1. Engineering maxim: **Local change. Predictable impact. Explicit dependencies. Shared truth. Isolated failures.**
2. Architecture scales with application complexity; architectural discipline does not.
3. Normal Vres interaction is Chairman-led conversation. The only user-facing control phrases are `start vres` and native `clear`.
4. Internal architecture/MCP/validation operations are never required user knowledge.
5. Every established-project adoption runs a deterministic read-only architecture audit.
6. Every established-project adoption produces one explicit incremental alignment plan against the Engineering Architecture Constitution and selected profile(s).
7. The exact alignment plan always requires canonical protected `vres-os:validator` Fable/high validation before architecture-changing migration or activation.
8. If protected Fable/high is unavailable, stale or overridden, the adoption plan is BLOCKED. No Sonnet/Opus/Codex/caller substitute is accepted.
9. Fable validates. Chairman remains user-facing. The user remains decision authority.
10. Existing projects use reversible strangler migration tranches, never giant repository reorganizations for cosmetic compliance.
11. New projects use the smallest appropriate profile; no empty enterprise-style layering.
12. Architecture checks should be machine-enforced wherever deterministic evidence is available.

## Deterministic architecture audit

The audit is read-only and never imports/executes project application code.

It currently provides bounded evidence for:

- fresh vs established maturity;
- proportional profile signals;
- top-level app/modules/domains/shared/platform presence;
- safely parseable Python and JS/TS dependency edges for recognized layouts;
- dependency cycles;
- shared → domain violations;
- shared → module violations;
- domain → module violations;
- sibling module dependencies;
- explicit private/internal cross-boundary imports;
- substantive module local-CLAUDE/public-API signals;
- large-file responsibility warning signals;
- bounded limitations when inventory/parsing is incomplete.

Stable finding IDs use `ARCH-001`…`ARCH-011`. Dependency findings include collision-resistant source/ref identity so separate violations remain individually addressable.

The audit additionally hardens:

- conventional packaged Python layouts such as `src/<package>/modules|domains|shared|platform`;
- Python relative and safely resolvable local absolute import edges without importing project modules;
- JavaScript/TypeScript side-effect imports;
- backend `platform -> domains/modules` upward-dependency violations;
- proportional profile selection so a tiny utility is not automatically forced into service layering;
- symlink refusal and bounded parse/inventory limits.

Known deterministic limitations are emitted as machine-readable evidence rather than hidden, including lexical-only JavaScript dependency scanning, unresolved custom Python import roots, unsupported source-language dependency parsers, over-budget files and truncated inventories.

The audit reports an exact digest over deterministic evidence. Alignment plans must bind to that digest so stale plans fail closed.

## Alignment plan contract

Every plan names target architecture profile(s).

Every material finding must be either:

- addressed by exactly one bounded migration tranche; or
- explicitly deferred/excepted with rationale, owner and revisit trigger.

Every tranche requires:

- key/title;
- findings addressed;
- dependency list;
- affected scope;
- target boundary;
- compatibility strategy;
- rollback;
- acceptance criteria;
- explicit non-goals.

The contract rejects:

- stale audit digest or stale constitution version;
- unknown, duplicate or audit-omitting target profiles;
- unknown profiles/findings;
- uncovered material findings;
- duplicate finding coverage;
- tranche self/unknown dependencies;
- dependency cycles;
- malformed/incomplete tranche/exception rows.

A valid deterministic contract returns:

`PLAN_READY_FOR_PROTECTED_VALIDATION`

and a canonical SHA-256 `plan_digest` bound to the exact JSON-compatible plan plus the current `audit_digest` and constitution version.

It also returns:

`activation_allowed = false`

Protected Fable/high remains mandatory. The protected review must bind to the exact audit/plan digests; any later audit or plan mutation invalidates that review and requires a new protected PASS before activation.
