## 1. Design result and real limitations

Authoritative Microsoft references, reviewed for this design: [MSRC Windows security servicing criteria](https://www.microsoft.com/en-us/msrc/windows-security-servicing-criteria), [service SID](https://learn.microsoft.com/en-us/windows/desktop/api/winsvc/ns-winsvc-service_sid_info), [virtual account service configuration](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-changeserviceconfigw), [service access rights](https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights), [session-0 interactive service limitations](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services), [named pipe access](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights), [pipe creation](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-createnamedpipew), [desktop ACLs](https://learn.microsoft.com/en-us/windows/win32/winstation/desktop-security-and-access-rights), [SendInput/UIPI](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput), [UAC](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/user-account-control/how-it-works), [credential providers](https://learn.microsoft.com/en-us/windows/win32/secauthn/credential-providers-in-windows), [secure attention at logon](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/security-policy-settings/interactive-logon-do-not-require-ctrl-alt-del), [Fast User Switching](https://learn.microsoft.com/en-us/windows/win32/shell/fast-user-switching), [Sandbox configuration](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file). These are platform design evidence, not actual guest proof.

Microsoft recognizes user, session and AppContainer boundaries; administrator controls the OS TCB, UAC is not robust isolation against an administrator. A service SID, job, high integrity, custom desktop, ordinary Hello challenge, consent dialog or successful sign-in alone does not establish exact transaction-specific owner intent. Do not misuse Winlogon, replace/wrap credential providers, install a driver, claim PPL, use interactive LocalSystem service or disable security settings. A distinct noninteractive service identity solves only broker isolation, not owner-input authenticity.

Selected conditional **guest-only design** (assistant design choice within owner-approved offline investigation, NOT an authorization to provision): same human operates two different synthetic guest principals in isolated logon sessions, one ordinary daily-test standard user and one clean protected operator session; only one active physical console at a time. This is a genuine cross-user/session candidate rather than asking an ordinary same-user UI to prove itself. The ordinary uncontained adversary runs as the SAME daily-test SID as the model's ordinary parent; the contained probe runs under that SID plus AppContainer. Neither is trusted merely for sharing the daily SID. The independent operator SID/session is deliberately different and protected. This does NOT establish resistance to arbitrary code running as the protected operator, or administrators/kernel, or solve the one-production-interactive-login owner-input problem. Preserve existing ordinary same-user adversary requirement on production; no claim it is reduced or satisfied by this guest split. No second production user/login/account approved. Do not call a two-guest-session pass production authority. Current Windows Sandbox supports isolation, but its actual ability to provide secure attention, separate nonadministrator interactive sessions and virtual service account/token is NOT_ESTABLISHED; its documented default user is an administrator. No automatic alternate VM, policy change or guest account creation. The design is conditional and the complete execution manifest remains NOT_READY.

## 2. Concrete guest role and access design

Logical names below are proposed fixture identities, not existing accounts or commands.
- R40FixtureBroker: dedicated own-process noninteractive Windows service with its own virtual account NT SERVICE/R40FixtureBroker (Windows account syntax uses backslash); service SID/restricted token candidate. No password collection, domain/network privileges, interactive logon, LocalSystem runtime or broad privileged proxy. SCM configuration, service binary/dependencies and directories owned by trusted guest setup authority; normal users cannot alter service executable, configuration, DACL, start/stop or user-defined control. Verify effective token user/service SID, restricted SID list, privileges and service session rather than trusting intended configuration. Service-SID behavior on the exact Windows build and any restart requirement are gates.
- R40FixtureDaily: guest standard user; ordinary uncontained fixed adversarial test process and original benign AppContainer/child test under this same daily SID. No admin membership, UIAccess or privileged token. AppContainer zero capabilities and nonbreakaway job; actual supervisor-owned suspended launch/verify/resume, exact image/dependencies, handles, child membership, conhost/ConPTY and teardown. No model-controlled paths, arguments, inherited authority handles, arbitrary process creation, or live native/DB/MCP.
- R40FixtureOwner: distinct guest-only authenticated clean operator session, same physical human owner, not a production account. Owner enters through actual OS secure-attention/logon path on isolated console, then uses a fixed manifest-pinned trusted renderer launched in that clean session, not a dialog in the daily session. No untrusted code under operator principal, remote input/automation, shared clipboard/desktop or UIAccess paths. Require actual observed user SID/logon SID/session ID, trusted console and renderer process/image identity; refusal if any path cannot be independently established. Ordinary same-user adversary from daily session must not access the protected UI or impersonate its input. Windows logon authenticates identity, not operation approval; protected renderer must independently display the entire exact proposal and receive a separate real Yes/No action.
- Trusted guest setup/observer/watchdog: fixture-only TCB, independent of both probe and normal user. Establish administrator-owned directory ancestry and precise DACLs, create only fixed enrolled test principals/processes when separately authorized, retain independently opened process/job/pipe observation handles and enforce deadlines. Runtime broker is not an unrestricted administrator. Any fixed suspended launcher privileges must be narrowly justified and measured, no arbitrary token-launch API; no assumed broad SeImpersonate or SeAssignPrimaryToken grant. Exact implementation and trusted runtime closure pending.

Access matrix: setup authority owns immutable binaries, configuration, root ancestors and service definition; broker may read/execute only fixed sealed code and use its own fixture scratch/mock state and lock; protected operator may read only pinned renderer and connect to exact owner channel (not change broker code, synthetic secret, receipt writer or installation); daily ordinary process may use fixed allowed fixture scratch and limited lock-contention control only; AppContainer/descendants have fixed stdio/child and allowlisted scratch, no owner channel, protected objects or lock authority. No writable ancestor/reparse/hardlink/ACL substitution, writable DLL/search path or dependency from daily/owner profile. Exact SIDs, ACLs and effective access checks not yet measured. Administrator is fixture setup TCB, not a claimed confined adversary. If current production user is administrator, no inference from this standard-user fixture.

Two separate communication surfaces: contained probe uses fixed original stdio/ConPTY handle inventory; owner channel is a narrowly scoped local authenticated endpoint. Named-pipe candidate: broker creates first instance, rejects remote clients, explicit DACL for service and exact enrolled operator logon SID, individual transfer rights (not generic write which includes pipe-instance creation), no ordinary daily/AppContainer access. Independent server/client identity verification binds peer token/user/logon SID, session and retained process/image identity; no PID/string or claimed SID alone. Stop on name squatting, wrong endpoint, reconnect/replay or unverifiable peer. No arbitrary commands, paths, token requests, approval booleans from model, or credential transport. Actual pipe security and minimum privileges require implementation/Windows observation. Existing owner_ui.c remains untrusted.

## 3. Integrated operation and one-lock choreography

Use only disposable fixture installation: proposed protected absolute synthetic LOCALAPPDATA under an administrator-owned guest directory, ending in VresOS exactly as original _installed_root(None) resolves it. Existing ordinary zero-length installation.lock, pending-install.json, old active-install.json, immutable snapshot and inert mock receipt/source/canary. All exact synthetic bytes, identities and paths enrolled in reviewed manifest; no production strings, DB driver, ConfigStore, native, hooks or real credential access. No alternative production root. Actual original lock module requires trusted Windows Python/stdlib/ctypes runtime. A fixed broker-owned lock worker running under the service identity is proposed if needed, with trusted absolute image/import paths, private environment set to manifest-pinned synthetic LOCALAPPDATA, isolated stdlib import closure, no product package initialization. It—not a caller returning bytes—must own the one handle and perform the mock receipt check and inert finalization within its scope. Broker retains worker identity; no general Python execution route, arbitrary script, caller path or token. Do not reimplement or mock the actual Windows lock. Exact candidate lock module is stdlib-only and its bytes are pinned above; no source modification.

States and invariants:
1. PREPARED → OBSERVED: independent fixture observation of original root/lock identity, journal/pointer/snapshot and expected receipt, protected scope, fresh operation ID and absolute monotonic deadline. Full fixed harmless proposal: exact synthetic target, old/target release labels, action, displayed consequences (inert mock completion only; no journal/pointer removal, no DB/native), observation identity. Bind exact display bytes and context internally. No owner digest entry.
2. OBSERVED → PRESENTED → OWNER_DECIDED: authenticated protected operator session and fixed renderer receive/render complete immutable proposal; genuine Yes/No, default deny, no synthetic control-looking text as decision. Fresh broker-generated challenge/operation ID, exact delivered display bytes/hash, observation, renderer/logon/session identity, deadline and decision bound together; nonce is correlation not authority. Reply can be consumed only once inside that protected operation, no export as bearer receipt. Missing/declined/replayed/mismatched/stale input or session loss -> HELD, no mutation. Do not hold install/DB locks while human reads or responds; retain original protected-owner contract.
3. OWNER_DECIDED → LOCK_HELD: after positive input, acquire actual original _hold_original_operator_lock exactly once. This calls OPEN_EXISTING share-zero noninheritable Win32 handle, compares file identity, revalidates root ancestors, requires pending journal, refuses restore journal. Independently revalidate admitted observation and exact journal, old pointer, snapshot, mock receipt and scope before consuming owner decision. No reuse after changed target/observation. No new lock, release/reacquire, ordinary runtime bypass or long waiting while locked.
4. LOCK_HELD → MOCK_RECEIPT_VERIFIED → MOCK_FINALIZATION_OBSERVED: same worker and same live _OriginalOperatorLock, call assert_live and revalidate enrolled identities/bytes at transitions; read exact inert mock receipt within scope, no real connection. A fixed scratch-only completion canary/record proves mock finalization work performed under that same handle. Positive path does NOT publish active pointer, remove journal, alter snapshot, invoke original PS production operation or grant authority. Independent competitor proves sharing refusal before receipt, between receipt and finalization, and at finalization barrier. No real finalization crash-atomicity claim. Do not pass mock receipt bytes to caller as permission.
5. MOCK_FINALIZATION_OBSERVED → RELEASED → CLEANUP: final recheck, exit original context exactly once, actual handle closes; independent contender can open exact same file afterwards. All errors, interruption, unexpected exit, missing observation or cleanup failure -> HELD, preserve original synthetic journal/pointer/snapshot bytes, no automatic retry or rollback. Positive completion record is fixture evidence only. If real production finalization later fails after possible pointer publication/schema advance, record actual state and explicit recovery disposition, do not claim old pointer necessarily survived.

Independent sharing control: use fixed separately launched competitor, not inherited handle or spoofed lock status, allowed to open existing exact synthetic lock under its fixture-only ACL but unable to replace/delete/re-ACL it or write other files. Before and after broker lock, open succeeds and closes without changing bytes. During each independent checkpoint, actual CreateFile sharing refusal (ERROR_SHARING_VIOLATION, not mere access denied/journal fence) on same file identity must be observed. Record requested access/share, raw result and observed stage. Existing private lock helper may normalize errors, so competitor independently records raw Win32 result. Verify root/file identity and broker handle continuity via independent observation, not timestamp/exit-code inference. No overlapping second successful exclusive handle. If unrelated contention or ACL denial prevents positive control, stop; no substitution. This is real original-lock qualification, not a synthetic replacement.
