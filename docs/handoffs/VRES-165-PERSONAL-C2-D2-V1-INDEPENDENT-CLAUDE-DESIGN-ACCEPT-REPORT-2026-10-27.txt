  New informational findings

  None of these is blocking.

  - N-1 (settle first, before any candidate evaluation): V1 does not say who authenticates registry updates.
    - If the head-store key signs them, then compromising the CAS key lets an attacker rewrite all four role entries, and the compromised
      store cannot commit its own replacement.
    - V1 relies on "root-controlled recovery principals" (V1:124) and a "publisher/root policy" (V1:118). Neither is a registry row with
      identity, key or purpose fields.
    - The publisher-withdrawal signer and the D3/D4 loader and observer purposes are also not enrolled.
    - Fix: add one sentence saying registry and epoch changes are signed only by the root or recovery principals. Add root, withdrawal-signer
      and reserved loader/observer rows. State how the root fingerprint is pinned in the H_0 ceremony.
  - N-2 (T2/T3 boundary): A PERSONAL Windows user is often a local administrator. V1:48 excludes admin as T3 but never says whether a UAC
    prompt, prompt fatigue or an auto-elevating binary counts as T2. Similarly, a wrapper that relies on the CurrentUser certificate store or
    user proxy settings is attackable at T2. P01 and P08 should require a standard-user day-to-day account (or an explicit residual) and a
    machine-scoped, pinned TLS trust store.
  - N-3 (P01–P12 testability): They are evidence categories, not test procedures. There is no adversary capability list (UI automation,
    overlays, token theft, DLL injection), no pass threshold, no evidence format, and no named adjudicator. Several terms are subjective (P11
    "proportional", P03 "authentic"). Also, V1:230 still says "independently accepted DESIGN V0 or revised V1", but V0 was DESIGN_REVISE.
    Remove "V0".
  - N-4 (accuracy):
    - V1:195 says install.ps1 "can auto-recover from a same-user journal". In fact install.ps1:114 refuses to run when a journal exists. Only
      the catch block (lines 314–347) restores in-process and deletes the journal. The conclusion still holds.
    - V1:185 says a derived candidate cannot masquerade as the original in v2. That is true at stage time only. verify_tree and _compare check
      SHA-256 only (release_artifact.py:414–455), and git_blob is shape-checked only (line 362), so a hand-written v2 manifest passes. This
      reinforces NF-07.
  - N-5 (sequencing and steady state):
    - H_0 requires a loaded-baseline observation (V1:128), which is loader-dependent D3/D4 capability. The first real post-D2 step is
      therefore a loader and observer feasibility check, not E/V implementation.
    - Because G includes the release and pins, V1 does not say what an ordinary non-policy release, or install.ps1 -Update, does to G after
      enrollment. Under R3 a mismatch means BLOCKED. State whether routine releases need ceremonies, which bears on proportionality for
      continuous PERSONAL development.
